# 0010. 状态项窗口 owner 派发与双通道点击策略（修正 ADR 0005）

> **状态：部分被取代** —— 本 ADR 的**决议 3**（辅助点击先按 `MenuBarItem.isOnScreen` 判定可达性）与**决议 6**（未参与合成的溢出项无可用辅助点击通道、返回 `ClickError.unreachableTarget`）已被 [ADR 0011](0011-secondary-click-session-event-routing.md) 取代：辅助点击改走会话事件流 + 目标窗口字段通道，不以 `isOnScreen` 分流，`unreachableTarget` 已删除。决议 1、2、4、5、7、8 继续有效。依 ADR 规范，正文保持原样不改写。

### 背景
[ADR 0005](0005-native-physical-coordinate-event-dispatch.md) 确立「100% 原生物理坐标事件派发」，要求 `MenuBarItemClicker` 一律以 `CGEvent.postToPid` 按真实窗口中心合成点击，并把左键与辅助点击视作同一条通道的两种参数。v0.0.10 真机实测发现该单一通道模型在两处与系统事实不符：

1. **派发目标不是真实应用**。状态项窗口在窗口服务器层**恒归控制中心宿主所有**。合成事件同时携带「目标进程」与「鼠标下窗口 / 待处理窗口」两组字段，二者必须自洽：若把目标进程写成 AX 反查出的真实归属应用，而窗口字段仍是宿主所有的那个窗口，接收方在自己的窗口表中找不到该窗口，事件被**静默丢弃**。真机 A/B 对照显示，改投窗口 owner 后由宿主完成菜单栏项激活并转交真实应用，第三方项（含被刘海挤占、**未参与合成**的溢出项）一次性恢复响应。
   - 注：`MenuBarAXResolver` 的「水平中心」配对修复仍然必要，但它决定的是**图元身份与 AX 元素定位**，与事件派发目标无关；把二者混为一谈，正是本 ADR 存在的直接原因。

2. **辅助点击没有可用通道**。私有字段通道**只认左键**：去掉私有字段、去掉「鼠标下窗口」字段对、改投真实应用进程三种变体下，右键事件均无效。而 AX 侧的 `AXShowMenu` 对第三方状态项返回 `actionUnsupported`。故 ADR 0005 所称「统一按窗口中心合成点击」对辅助点击并不成立。

   该结论曾有一次取证缺陷：早期测试**早于**「投递前须等待穿透标志生效」这一修复，存在被自有视口吃掉事件而**假阴性**的可能。v0.0.10 以**带有效性对照的三通道探针**重测（内建刘海屏，同时跑：可见项坐标右键作对照 + 未合成项坐标右键 + 未合成项私有字段右键），结果：**对照项弹出原生菜单（通道可用），未合成项的 4 项 × 2 通道共 8 格无一送达**。二者并存才能排除「取景框本身失效」的解释，故决议 6 的平台边界自此**证据充分**。

### 决议
1. **派发目标恒为状态项窗口的 owner**：`MenuBarItem.clickTargetPID` 恒返回 `processIdentifier`；`sourcePID` 只服务于图元归属与 AX 元素定位，**不参与点击派发**。
2. **左键单击走宿主激活通道**：单边左键事件经私有字段与 `postToPid` 投给窗口 owner。该通道对全部状态项有效，包含未参与合成的溢出项。
3. **辅助点击必须先判定可达性，再决定是否投递**，判定依据为 `MenuBarItem.isOnScreen` —— 它表达「窗口服务器是否已为本屏合成该窗口」这一物理事实，不是启发式阈值：
   - **已合成** → 系统事件流通道：按窗口实时中心的屏幕坐标投递右键，由窗口服务器自行路由；
   - **未合成** → Fail-Fast 返回 `ClickError.unreachableTarget`，**不派发任何事件**（理由见决议 6）。
4. **投递期间须临时穿透自有视口，且必须等待穿透标志在窗口服务器侧生效后**才可派发；否则事件被自家视口吃掉（实测：立即派发对可见项同样失败）。
5. **穿透状态按进入前的真实状态逐屏精确还原**，不得一律复位为其反面：平直外接屏折叠常态本就要求穿透为开启。
6. **平台边界（已取证）与严格语义**：未参与合成的溢出项**不存在**可用的辅助点击通道（背景 2 已用带有效性对照的取证排除假阴性）。故此类项上的辅助点击**不派发任何事件**，返回 `ClickError.unreachableTarget` 交由调用方呈现。
   - **严禁改发左键冒充右键**：左键在部分应用是「立即动作」而非菜单（静音 / 暂停 / 开关），冒充会与用户「我要菜单」的意图相悖，造成非预期副作用。「左键与辅助点击弹出不同菜单」的应用（如以 `popUpContextMenu()` 实现、左键无响应的 Electron 系托盘）尤其不能靠冒充解决。
   - **失败不得静默**：岛内图标据 `.failure` 触发横向 Shake 与触觉反馈（`IslandIconCell.run`），用户能得到「此项不可右键」的明确信号。
   - **必须知情的后果**：刘海屏上的岛内项恒未合成，因此**该屏岛内辅助点击在当前平台能力下弹不出菜单**。用户若要某应用的上下文菜单，应在无刘海的外接屏上直接右键其原生可见的同类项。
7. **事件字段唯一构造器**：点击事件的字段组装（私有字段、按键号、`clickState`）一律由 `MenuBarClickEventFactory` 提供，生产路径与诊断路径不得各自拼装。
8. **不提供左键双击**：`MenuBarClickKind` 只有 `.single` 与 `.secondary` 两种。双击是 `.leftMouseDown` 的 `clickCount == 2`，与辅助点击（触控板双指 = 鼠标右键，macOS 上二者是同一个操作）正交；一旦按 `clickCount >= 2` 分流，双击间隔内对同一图标的第二次单击会被误吞，表现为「单击时灵时不灵」。
9. **不可达即返回错误**：`windowID == 0` → `ClickError.invalidWindow`；实时 frame 不可得 → `ClickError.frameUnavailable`；事件构造失败 → `ClickError.eventCreationFailed`。不得静默改用其它目标或其它通道。

### 理由与权衡
本决议用「目标进程与窗口字段必须同属一个进程」这一自洽性约束换取可达性：代价是宿主必须代为转发，因而左键与辅助点击在宿主侧的语义差异被抹平 —— 这正是决议 6 平台边界的来源，也是辅助点击必须分流到坐标通道的原因。

相比 ADR 0005 的单一通道，双通道把「可达性」显式建模为分流条件，而不是用统一通道加兜底猜测去掩盖系统事实：分流依据 `isOnScreen` 是可观测的物理合成状态，不是容差或阈值。同时，本 ADR 明确划定 `isOnScreen` 的**唯一**用途 —— 判定点击事件能否按坐标送达；这不是对 [ADR 0003](0003-pure-physical-geometry-overflow.md) 「溢出判定严禁依赖 `!isOnScreen`」的松动，二者作用域互不重叠。

取严格语义而非「不可达时改发左键」是刻意的：前者把平台边界的真实形状暴露给用户（Shake + 触觉即「此项不可右键」），后者则是用一种语义上错误的动作去掩盖它。宁可让用户在刘海屏上得不到菜单，也不让他在不知情的情况下触发一个「立即动作」。

### 影响
- 修正 [ADR 0005](0005-native-physical-coordinate-event-dispatch.md) 的决议；0005 关于「拒绝移动三方窗口以篡改菜单锚点」的判断继续有效，`NativeMenuAnchor` 术语不变；
- 与 Issue #55 中「状态项点击目标修复（Real Owner PID）」一节的**诊断方向相反**：该节主张派发目标取真实归属进程，本 ADR 依据真机 A/B 对照主张取窗口 owner。依 `docs/agents/issue-tracker.md` 的约定不以代码反改 issue 正文，差异须以 issue 评论形式回填，避免静默修正历史；
- 相关实现见 `MenuBarItem.clickTargetPID`、`MenuBarClickEventFactory`、`MenuBarItemClicker`、`IslandIconHitZone`（`IslandSecondaryClickRouter`）、`IslandHostingView`；
- 架构不变量表述见 `AGENTS.md` §3.4，字段语义见 `docs/DOMAIN_MODEL.md` §2.1。
